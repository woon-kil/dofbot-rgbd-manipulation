근거 문서: `docs/261112-0748-설계진단보고서.md`. 사용자 지시: "진단보고서를 프로젝트에 반영해".

## 원칙
- **결정이 필요한 항목은 내가 정하지 않는다.** 자세 확보 방식(P0-1), 베이스 기준 방식(P0-2), 오차 임계값 숫자(P0-3)는 사용자·실측이 정할 일이므로 ADR을 `PROPOSED`(옵션과 영향)로만 쓰고 로드맵에 "미결" 표시를 남긴다. 임의 숫자를 넣지 않는다.
- 결정이 필요 없는 항목(문서 불일치, 코드 결함, 증거 항목 추가, 위험 등록부, 저장소 위생)만 실제로 고친다.
- 하드웨어 접속·명령 없음. git init·커밋은 하지 않는다(사용자 요청 범위 밖).
- codex 자문은 사용 한도 소진(2026-11-13 21:08 이후 가능)으로 받지 못했다. 이 플랜은 codex 검토 없이 진행한다.

## 목표 / As-Is / To-Be
- 목표: 진단보고서 중 결정이 필요 없는 항목을 프로젝트에 반영하고, 결정이 필요한 항목은 사용자가 고를 수 있는 옵션 문서로 만든다.
- As-Is: 문서 불일치 3건, `se3.multiply`의 직교성 미검사, 동어반복 테스트, G01 증거 항목에 깊이 모드 없음, `.gitignore` 없음.
- To-Be: 위 항목이 해소되고 `validate_design.py`와 단위 테스트가 통과하며, 미결 3건(자세 확보, 베이스 기준, 충돌 검사 범위)이 ADR-005에 PROPOSED로 있다.

## 접근 방법 비교
| 안 | 장점 | 단점 |
|---|---|---|
| A. 결정 불필요 항목만 반영 + 결정 항목은 PROPOSED (채택) | 되돌리기 쉽고 임의 결정이 없다 | P0는 사용자 결정 전까지 열려 있다 |
| B. 보고서 권고를 전부 내가 결정해 반영 | 한 번에 끝난다 | 하드웨어·안전 결정을 근거 없이 확정한다 |
| C. 보고서만 두고 반영 보류 | 위험 없음 | 지시와 다르다 |
