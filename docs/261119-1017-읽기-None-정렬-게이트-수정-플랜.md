# 다음 수정 묶음 플랜 v1.1 (연속 읽기 None, 정렬 NG 자동 N, 정렬 여유, clock_log) — 자문 04 보강 반영, advisor 검토 대기

**계획이다. 사용자 결정(§5)과 advisor 검토 전에는 구현하지 않는다.** 배경: 새 승인 실행 #1(`261119-094728`) 같은 지점 재발 2/2, 정렬 NG에서 y 진행. 상세 `docs/261119-1011-재실행-어댑터-읽기-None-재발-이슈보고서.md`. 코드는 `c1be47e` 그대로이고 스냅샷 `261119-lift2` 유효(구현 즉시 무효).

## 1. 확인된 사실 (코드·기록을 읽고 확인)
1. **None 로그 패턴(기록 사실):** `lift.adapter_logs`에서 J2 어댑터 둘은 시작값 읽기 직후 `run_move`의 `before = ads[j].read_position()`이 None(`g01_p2k_test.py:106`), J4 어댑터는 `_stage_idx`의 원시 읽기 직후 `read_start`가 None(`g01_lift_hook.py:67`, `gripper_adapter.py:69-76`). 연속 읽기 가설은 **참고용**이다.
2. **`before`가 None이면** `width0 = abs(tgt - (before if before is not None else tgt)) = 0`이라 `need_react=(width0 >= 5)`가 꺼져 무반응 검사·재전송이 조용히 꺼진다(`g01_p2k_test.py:109-110` 부근). 이번 J2 이동 두 개가 그 상태였다.
3. **정렬 질문 구조(코드):** 러너가 `[정렬 확인]` 줄을 출력하면(`g01_p2k_test.py:242`) Mac 다리가 그 줄을 보고 정렬 보고를 계산해 화면에만 띄운다(`g01_lift_bridge.py:100-105`, "Jetson 전달 없음"). 러너는 곧바로 `ask(...)`로 사람 입력을 기다린다(243행). 보고 계산 1~2 s 동안 프롬프트가 이미 떠 있어 보고를 읽기 전에 y를 입력할 수 있고, NG 규칙은 코드가 강제하지 않는다.
4. **읽기 순서(코드 확인, 자문 04 요청):** `raw_set`은 서보 1·2·3·4를 간격 없이 차례로 읽는다(`g01_p2k_test.py:344-348`). `_stage_idx`는 `_raw(J2)`·`_raw(J4)`로 `raw_set`을 연달아 두 번 부르므로 마지막 읽기가 J4이고, 곧바로 `_adapter`의 J4 `read_start`(SDK 읽기)가 같은 서보 4를 간격 없이 다시 읽는다. J2 어댑터는 `read_start`(J2) 직후 `read_position`(J2)이 같은 서보를 간격 없이 읽는다. 이동 중 폴링은 1·2·3·4를 순환해 **같은 서보의 연속 읽기 간격이 약 0.1 s**(`POLL_MS`)다. 이 구조는 자문 04의 더 날카로운 가설 **"같은 서보 번호를 간격 없이 연속으로 읽으면 두 번째가 None"**과 일치한다(미확인, 참고용).
5. **None 집계(사후 분석, 참고용, 결정 근거 아님):** 04의 집계(실기기 91건, 중복 제거): 계획 이동 직전 첫 읽기 0/1,328, 들어올림 이동(카운트다운 0, read_start 직후) 4/4, 들어올림 셋째 이동 `read_start` 2/2, 이동 중 폴링 1,047/201,573(0.52%). 내 집계(어댑터 로그 전체, 0.65% = 729/111,633)와 집합이 달라 숫자가 다르다.
6. **`clock_log`:** `done()`(`g01_lift_hook.py:131`)에서만 저장되어 `GripperTestError` 같은 실패 경로에서는 None이다.
