## 원인
`cv2.phaseCorrelate`(OpenCV 4.14.0)는 입력 배열을 제자리에서 수정한다(창 함수를 곱함). 입력 크기가 `getOptimalDFTSize`와 같으면(100·160·1280) 입력이 바뀌고, 패딩이 필요한 크기(420)에서는 바뀌지 않는다(합성 시험). 뷰를 넘기면 원본 배열이, 복사본을 넘기면 복사본이 바뀐다. 탐색 스크립트가 같은 사진 배열을 재사용하며 현행 영역(480~900)을 먼저 계산한 뒤 그 오른쪽 끝인 새 영역(800~900)을 계산했고, 새 영역은 이미 창 함수가 곱해진 데이터로 계산됐다(순서 의존). 타일 탐색값도 같은 오염이다. 사용자 보고서의 "연속 복사본은 항상 같은 값(0.74)"도 앞선 뷰 호출이 오염시킨 배열에서 나온 값이라 틀렸다. 합성 시험에서 "복사본도 변경됨: True"가 이미 나왔는데 문구에 반영하지 못했다.

## 교훈
1. `cv2.phaseCorrelate`에 넘기는 배열은 호출마다 새로 만들어 버린다. 복사본이어도 바뀐다. 시험은 '입력 불변'이 아니라 '순서 무관'으로 쓴다.
2. 수치가 반복 호출에서 달라지면 사진이 아니라 도구를 먼저 의심한다. 서로 다른 두 결과가 한 세션에서 나오는데 원인을 확인하기 전에 영역 문구를 먼저 쓴 것이 이 이슈를 키웠다.
3. 앞서 쓴 '깨끗한 값'을 확인 없이 믿지 않는다. `p1_preflight` 참고값의 '깨끗한 값 0.865'는 이미 변경된 배열로 계산한 틀린 비교값이었다(0.893이 올바른 값).
