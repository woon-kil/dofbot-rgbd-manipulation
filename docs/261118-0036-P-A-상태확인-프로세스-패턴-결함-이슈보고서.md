# P-A 상태 확인이 드라이버 프로세스를 못 찾은 이슈 (P-A 시험 1회차, 2026-11-18)

## 현상
자동 종료 시험(M1'', MAXSEC=45)에서 `pa_driver status`가 start 직후 0.3 s에 "드라이버 프로세스 없음"을 돌려줬고, 오케스트레이터는 드라이버가 꺼진 것으로 판단해 곧바로 snap했다. snap은 성공했고 `auto_exit_snap_failed=False` → 사전 등록 M1'' FAIL. 실제로는 드라이버가 살아 있었고(타임아웃 INT 전, driver.log의 SIGINT는 stop이 보낸 것) **자동 종료 자체는 이번 세션에서 시험되지 않았다.**

## 원인
- `pa_driver.sh`의 상태·정리 확인은 `pgrep -f "[o]rbbec_camera_node"`를 썼다. 실제 드라이버 프로세스는 **`component_container`**(ComposableNode)다(증거 `evidence/G06/pa_261118-001026/driver_cycle3.log`: `:3` "process started [component_container-1]", 끝 `process has finished cleanly [component_container-1]`, SIGINT 시각 1794929592.01은 stop이 보낸 것으로 timeout INT 로그 없음. **p620 원본 driver.log는 start마다 덮어써지므로 이 복사본이 1차 증거**). 패턴이 살아 있는 드라이버와 한 번도 맞지 않았다.
- 이 패턴은 원본 `g01_gemini_check.sh`(`pgrep -f "[o]rbbec_camera_node"`로 종료 확인)에서 가져왔다. 원본에서는 kill 뒤 "드라이버 없음"이 항상 나오므로 **원본의 종료 확인 메시지는 정보가 없었다**(P-A 0단계의 "드라이버 없음(...)"도 같은 이유로 확인이 아니었다). 종료 자체는 `pkill -f ... gemini_330_series`(ros2 launch 명령줄)가 맞아 정상 동작했다.
- 시험 설계도 취약했다: 상태 확인이 '없음'이면 타임아웃 시각 이전에도 바로 snap해 버렸다.

## 수정 (스냅샷 `261117-pa3`)
`pa_driver.sh`의 상태·정리 확인 패턴을 `[c]omponent_container|[o]rbbec_camera_node`로 바꾸고, 오케스트레이터는 타임아웃 시각(launch+45 s) 전에는 '꺼짐'을 인정하지 않도록 첫 polling을 26 s 늦췄다(start 반환은 launch보다 약 17 s 늦다). 수정만으로는 검증되지 않는다 — 살아 있는 드라이버에서 `status`가 '있음'을 내는지 확인하는 재시험이 필요하다(미검증).

## 같은 패턴을 쓰는 다른 스크립트(목록만, 고치지 않음)
`scripts/g01_gemini_check.sh:32·33`, `scripts/g01_gemini_remote.sh:32·33`, `scripts/pa0_g01_gemini_check_timed.sh:46·48`의 `pgrep -f "[o]rbbec_camera_node"`. kill 뒤 '드라이버 없음'을 출력하는 확인이라 **항상 '없음'이 나오는 정보 없는 검사**다(실제 종료는 `pkill -f ... gemini_330_series`가 맡아 정상). 원본 불변 원칙(36 s 방식 증거 유지)에 따라 수정하지 않았다.

## 교훈
- 상태 확인 패턴은 **'살아 있는 대상에 맞는가'**를 먼저 확인한다(부정 결과가 항상 나오는 검사는 검사가 아니다). 원본 스크립트에서 패턴을 가져올 때 원본의 확인이 실제로 양성을 낸 적이 있는지 본다.
- 시험 설계는 '완료' 신호를 하나의 검사에만 의존하지 말고 시간 조건(타임아웃 이후)을 함께 건다.
- 로그·증거 파일은 start마다 덮어쓰지 않는다(pa4: `driver_<epoch>.log`, `driver.log`는 최신을 가리키는 링크, 오케스트레이터가 세션 끝에 복사).
