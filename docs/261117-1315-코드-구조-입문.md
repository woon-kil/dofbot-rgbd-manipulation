## 1. 어디서 무엇이 도는가 (`docs/architecture/system-design.md` 실행 토폴로지, ADR-006)

| 호스트 | 하는 일 | 연결 |
|---|---|---|
| **Mac**(이 저장소) | 이동 계획·충돌 검증·분석, 실행 래퍼(`scripts/`), 증거 저장(`evidence/`) | Jetson·p620에 ssh |
| **Jetson** | DOFBOT SDK로 서보 명령·회독, DaBai(손목 카메라) 드라이버 | Mac에서 `ssh -t`로 시험 코드를 실행 |
| **p620**(공유 GPU 서버) | Gemini 335L(고정 카메라) 취득, 이 프로젝트 전용 docker 컨테이너 안에서만 | Mac에서 ssh·scp로 사진 1장씩 가져옴(`scripts/p1_m3_gemini_photo.sh`) |

- Mac이 실제 회독으로 이동 계획을 만들고 안전 게이트를 통과시킨 뒤, 승인된 시험만 `--real`로 Jetson에서 실행한다(`scripts/*_run.sh` 머리말).
- 두 호스트의 시계는 별개이므로 장치 간 타임스탬프를 직접 비교하지 않는다.

## 3. 시험 하나가 흘러가는 순서 (예: P2k Run)

1. `docs/gates/`에 설계·승인 요청 문서 → advisor 검토 → 사용자 승인.
2. 판정 규칙(검출기·문턱)을 결과 보기 전에 사전 등록.
3. `scripts/`의 시험 코드·래퍼 구현 → 가짜 서보 시험 → `plan_check`(충돌 모델) → 스냅샷.
4. `--check`/dry run으로 읽기만 확인 → 승인 뒤 `--real`.
5. 기록이 `evidence/**/raw/`에 생기고, 인용할 것만 `tools/verify_records.py --add`로 `evidence/records/`에 복사.
6. 분석 → 결과 문서 → `PROJECT-STATUS.md` 갱신 → 커밋.

## 4. 처음 실행해 보기

```
.venv/bin/python -I -m unittest discover -s tests     # 단위 테스트 (약 1~2초)
python3 tools/direction_check.py --status             # 방향 점검 상태
python3 tools/verify_records.py                       # 기록 복사본 해시 검증
```

환경은 `requirements.txt`(numpy·opencv-headless·scipy)로 만든 `.venv`다. Jetson 전용 라이브러리(`Arm_Lib`, ROS)는 Mac에 설치하지 않는다. 주의: `scripts/` 래퍼마다 기본 파이썬이 다르다. 예를 들어 `g01_p2k_run.sh`는 이 저장소의 `.venv`를 쓰지만 `g01_5b4_s42_run.sh`는 옛 경로(`~/projects/simple-vision-tech-poc/.venv`)를 쓴다. 막히면 환경변수 `P1_CHECK_PY`로 `.venv/bin/python`을 지정한다.

## 5. 이 문서의 한계

- `scripts/` 안 파일별 역할은 일부 머리말만 확인했고 전부 읽지 않았다.
- 파일 이름과 개수는 날짜가 지나면 어긋난다. 새 시험이 생기면 이 표의 `scripts/`·`evidence/` 줄만 갱신하면 된다.
